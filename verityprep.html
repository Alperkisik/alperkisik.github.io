    Summary

    Verityprep came out of one need, giving Veritas Academy's students digital exams and digital question banks, and went far beyond it. Today it is a full preparation system for students applying to universities abroad, and the institution is taking it to the global market. Thousands of students and hundreds of teachers have used it, and they still do.

    I started the project in November 2024 and I am its lead developer and largest contributor. I built it according to the institution's business needs and the requests that came in, and I kept improving it from user feedback.

    Features

    Public site

    • Marketing and information pages in three languages: Turkish, English and Montenegrin
    • Course pages per exam type, with previewable sample exams
    • Exam packages, coupons and subscription pricing, with online payment and 3-D Secure
    • Score calculators and free resources for each exam board

    Student Portal

    • Full-length timed digital exams for AP, SAT, IB, IMAT, ACT, IELTS, Bocconi and Proficiency, plus Turkish school-curriculum support
    • Digital question banks by topic and subtopic, with bookmarks, saved questions and mistake collections
    • Homework: solving, document upload and free response submission with AI-assisted grading
    • Step-by-step AI solutions, AI guidance panels and an AI credit ledger
    • Spaced repetition vocabulary training, progress reports and solved-question statistics
    • Live lessons over Zoom, lesson recordings, subscriptions, invoices and refunds

    Teacher Portal

    • Question bank and exam management per course
    • Exam evaluation and grading, including free response answers
    • Student tracking, question-solving statistics and a guidance panel
    • Homework authoring from the question bank
    • Lesson reports, monthly reports and a question-defect workflow

    Parent, Consultant and Content portals

    • Parent portal with its own login, multi-child switching, exam status, lesson reports and monthly student reports
    • Consultant portal for student enrolment and exam entitlements
    • Content-admin portal where editors build exams and question banks, including an AI-assisted pipeline that converts exam documents into digital exams

    Development Process

    On the Architecture part, I designed my own variant of vertical slice architecture for ASP.NET Core. Classic vertical slice puts a whole feature in one file; I did the opposite. One class per file, all files under one feature folder, and the folder is the slice. Every slice has three fixed layers, entry to service to repository, and each layer has a written contract about what it is not allowed to know. The part that is specific to ASP.NET Core is that a slice owns two entry points at once: a Minimal API endpoint class and an MVC action written as a partial class of its Area controller. There is no mediator; slices are discovered by assembly scanning at startup, so a new feature needs no registration file.

    On the Back-End part, the application is a single .NET 8 project organised into nine Areas, one per portal. Existing ORMs were making the portal slow, so I wrote my own stored-procedure-first ORM over raw ADO.NET, in the spirit of Dapper. In it a repository method name is the stored procedure name, and a dotted column alias maps into a nested property, so a procedure returning several result sets can be assembled into one object. I also wrote my own error handling instead of using the framework's. Every service returns a result wrapper, so failure is part of the signature rather than an exception that escapes it, and my own middleware catches exceptions and error status codes, decides which portal the request belongs to and sends the user to that portal's error page. Requests coming from JavaScript get the result envelope instead, which my own fetch and toast layer turns into a message on the page.

    On the Authentication part, we were using ASP.NET Core's own login system and many users were having trouble reaching the student and teacher portals. I replaced it with my own: a self-contained encrypted authentication ticket, close to JWT in spirit, carrying the user's identity, role, branch and expiry in a single cookie. Custom middleware decrypts it on every request and builds the ClaimsIdentity itself. On top of it I built role policies, a commercial tier axis and data-driven permissions down to a single course or a single exam.

    On the Front-End part, all pages are Razor views with Bootstrap, vanilla ES modules and jQuery, with KaTeX for mathematics. The JavaScript mirrors the backend slicing: the exam application has its own core, components, services, state and phases folders, without a framework. The exam interface is a faithful re-creation of the College Board Bluebook experience, shared between exams and question banks, so students practise in the interface they will be tested in. Colours come from CSS custom properties, which made light and dark theming possible across the portals. I kept working on the interface throughout the project, because user experience is where I put most of my attention: a student sitting a timed exam cannot be asked to tolerate a rough screen.

    On the Database part, business logic lives in roughly 400 stored procedures on MS SQL Server, with the scripts checked into the slice that owns them. The platform runs on SQL Server Express with four cores, so performance had to come from the data layer. I profiled the live workload, found procedures taking four to six seconds, and fixed the causes: missing indexes, two large tables stored as heaps, and queries written in a way that defeated index seeks. I added covering indexes, gave the heaps clustered keys, rewrote the slow procedures, cached the reference data behind every page layout and removed a sync-over-async call. There was repair work too, rebuilding data that had gone inconsistent and improving table designs that had outgrown their original shape.

    On the Internationalisation part, the public site is published in three languages: Turkish, English and Montenegrin. I built this without resource files. Each language has its own controller, its own route table and its own views, and the language lives in the URL slug itself. Every page knows its own address in the other two languages, so the switcher takes a visitor to the equivalent page rather than back to a homepage, and the layouts emit alternate language links for search engines. The sign-in page and the error pages choose their language from the visitor's browser language preference.

    Elsewhere in the project, the same approach produced an email system with its own queue and logging, direct clients for four AI providers rather than their SDKs, nine background workers with hand-written scheduling, endpoint discovery that publishes the live route table, a sitemap and meta tag builder for SEO, a spaced repetition scheduler for vocabulary training, and Zoom integration including its OAuth and signing.

    Update Entry

    Entry Date : 12.03.2025

    verityprep.co.uk was added, for use in the United Kingdom. This site was requested in English only, which the three-language codebase was not built for: every page existed in Turkish as well, and the language switcher was part of the layout. To solve it I built a publish option system. The publishing target is part of the build, and it decides what the application registers: for the English-only target the Turkish route table is never registered at all and the language switcher is suppressed, so the site has no Turkish pages to reach rather than Turkish pages that are merely hidden. One codebase now ships as three separate sites.

    Its interface is the previous design of the public site, so verityprep.co.uk is also a record of what the main site looked like before its recent redesign.

    Entry Date : 15.10.2026

    Since February 2026 I have been developing this project together with Claude Code, and I optimised that workflow to spend fewer tokens and get more out of it. Rather than letting an agent search the repository, I documented it: a routing menu that lists every feature with its status and nothing more, and a documentation set inside each slice covering its purpose, files and decisions. I also separated the roles, so the main thread orchestrates and never writes code, writer agents make the edits, and review agents check the result in parallel. Hooks enforce the rules that documentation alone could not, including keeping database access read-only.
